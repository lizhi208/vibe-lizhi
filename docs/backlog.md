# 功能冻结令 · Backlog（第 6 天起生效）

> **只修不添。** 第 6 天（2026-10-12）起功能冻结，新想法全部记入本文件，
> Demo Day 讲「我们忍痛砍掉的功能」——那也是故事的一部分。
>
> 砍掉不是失败，是排优先级。砍得清楚，比做得一塌糊涂强。

## 冻结边界（第一版不做的）

| # | 功能 | 砍掉的理由 | Demo Day 讲法 |
| --- | --- | --- | --- |
| 1 | 用户登录态 / 权限 | PRD 定位「免登录演示型」，加登录会拖慢 Demo 节奏；演示账号写死在 schema.sql | 「为了让你 30 秒能上手，我们砍了登录——代价是卖家 id 写死，Demo Day 我们会讲这个取舍」 |
| 2 | CORS 白名单收紧 | 当前 `cors()` 默认放行 `*`，开发期省事；生产前必须换白名单 | 记为技术债，列在评审记录-day5 的「上会项」里，Demo 时一句话带过 |
| 3 | 访问量防刷 | `POST /api/stats/visit` 无鉴权可被脚本刷高，但 Demo 只看走势 | 「我们知道能刷，Demo 前会手动归零——防刷是工程题不是产品题，留到下一版」 |
| 4 | 商品收藏 / 关注 | 与「快速成交」主线无关，加表加接口拖周期 | 「砍掉是因为它会让首页变重——我们要的是下单快，不是逛得久」 |
| 5 | 订单状态机扩展 | 当前只有 ON_SALE→LOCKED→SOLD 三态，缺取消/超时释放 | 「三态够讲清故事，超时释放是下一版的工程题」 |
| 6 | AI 多轮对话 | `POST /api/ai/answer` 标 TODO，多轮要管 session 上下文，成本高 | 「我们做了单轮草稿，多轮砍掉是因为上下文管理会吃掉一半工期」 |
| 7 | 以图搜同类 | PRD 边界外，需向量检索基础设施 | 「进阶功能，明确不纳入第一版」 |
| 8 | 在线支付 / 物流 | PRD 硬边界，成交仅改状态 | 「这是产品定义，不是技术取舍」 |

## 冲刺优先级（冻结后只剩修 bug）

1. **必须修**：交叉验收发现的重档缺陷（契约不符 / 崩溃 / 数据错误）——全清零。
2. **建议修**：体验类小问题，按 Demo Day 演示路径取舍——演示用不到的可以放着。
3. **不做了**：上表 8 项，全部留到下一版。

## 忍痛清单（Demo Day 备用台词）

> 演示时如果被问「为什么没做 XX」，照下面答：

- **没登录** → 「演示账号写死，砍登录换 30 秒上手」
- **AI 接 answer 没接** → 「单轮草稿够讲清 AI 辅助发布的故事，多轮留下一版」
- **能刷访问量** → 「防刷是工程题，Demo 只看走势，我们不藏」
- **订单不能取消** → 「三态状态机够 Demo，超时释放是下一版工程题」
